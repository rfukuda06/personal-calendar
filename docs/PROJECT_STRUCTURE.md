# Project Structure

Map of every important folder: what lives there, what doesn't, and how it connects to neighbors.

```
personal_calendar/
├── docker-compose.yml       # Postgres service definition
├── .env                     # Local secrets (DB URL, Google OAuth) — gitignored
├── .env.example             # Template for .env — committed
├── prisma/                  # Database schema & migrations
├── src/
│   ├── auth.ts              # NextAuth v5 config (providers, callbacks)
│   ├── middleware.ts        # Route protection (runs on /calendar/*)
│   ├── app/                 # Next.js pages + API routes (routing by filename)
│   │   ├── api/             # Server endpoints (/api/events, /api/todos, ...)
│   │   │   └── auth/[...nextauth]/  # NextAuth GET/POST handlers
│   │   ├── signin/          # /signin page
│   │   └── calendar/        # The actual calendar UI pages
│   ├── components/
│   │   ├── calendar/        # Feature components (DayView, WeekView, EventDialog...)
│   │   └── ui/              # shadcn primitives (Button, Dialog, Select...)
│   ├── lib/                 # Pure logic shared across the app
│   ├── schemas/             # Zod schemas — shared between forms and API routes
│   ├── types/               # Ambient TypeScript declarations (e.g., augmenting Session)
│   └── generated/prisma/    # Auto-generated Prisma client — never hand-edit
├── docs/                    # This folder: beginner-friendly docs
└── public/                  # Static files served as-is (favicons, images)
```

## The key folders

### `prisma/`

Holds `schema.prisma` (the database shape — all our tables and relations) and `migrations/` (versioned SQL files). Run `npx prisma migrate dev` after editing the schema to apply the change to the local DB. Prisma also *generates* a typed client into `src/generated/prisma/` whenever the schema changes.

### `src/app/` — Pages & API (routing by filename)

Next.js App Router: the folder structure **is** the URL structure.

- `src/app/page.tsx` → `/`
- `src/app/calendar/week/[date]/page.tsx` → `/calendar/week/2026-05-01`
- `src/app/api/events/route.ts` → `GET/POST /api/events`

Conventions:
- `page.tsx` — a page component (renders HTML).
- `layout.tsx` — wraps all child pages (e.g., sidebar + header).
- `route.ts` under `/api/` — a server endpoint, exports `GET`, `POST`, `PATCH`, `DELETE` functions.
- `[bracketed]` folders — dynamic segments, available as `params` in the page.

### `src/app/api/`

Every server endpoint. Each route file:
1. Reads the NextAuth session to get `userId`.
2. Validates the request body with a Zod schema from `src/schemas/`.
3. Uses the Prisma client from `src/lib/db.ts` to read/write the DB.
4. Returns JSON.

Never import API route files from components — components call them via `fetch`.

### `src/app/calendar/`

The UI. Three route folders: `day/[date]/`, `week/[date]/`, `month/[date]/`. A shared `layout.tsx` renders the sidebar and view-switcher; each page is a thin wrapper around the matching view component from `src/components/calendar/`.

### `src/components/calendar/`

Feature components specific to this app:

- `DayView.tsx`, `WeekView.tsx`, `MonthView.tsx` — the three calendar views. Day and Week are both thin wrappers around `DaysView.tsx`, a shared hour-grid component that accepts an array of 1–7 days.
- `CalendarHeader.tsx` — top bar with the Day/Week/Month switcher and per-view prev/next/today navigation.
- `BigEventBar.tsx` — the all-day strip at the top of day/week.
- `TodoList.tsx` — right-rail todo checklist shown in day view.
- `EventDialog.tsx`, `BigEventDialog.tsx` — create/edit dialogs for timed events and big events. Same RHF + Zod + category-chip layout, different shells (floating card next to the grid for events; centered modal for big events). Todos don't use a dialog — they're created and edited inline inside `TodoList.tsx`.
- `RecurrenceEditor.tsx` — the UI for building an RRULE (daily/weekly/custom).

### `src/components/ui/`

Generic, app-agnostic primitives installed by `shadcn/ui`: `Button`, `Dialog`, `Select`, `Popover`, `Calendar` (date picker), etc. Feature components compose these.

### `src/lib/`

Pure logic, no UI:

- `db.ts` — the singleton Prisma client.
- `auth.ts` — NextAuth config (Google provider, session callbacks).
- `time.ts` — Luxon helpers: convert UTC ↔ LA, compute day/week/month ranges.
- `recurrence.ts` — expand an RRULE for a date range, apply exceptions, handle "edit this / this+future / all."
- `utils.ts` — the `cn()` class-name helper from shadcn.

### `src/schemas/`

Zod schemas, one file per entity (`event.ts`, `bigEvent.ts`, `todo.ts`, `category.ts`). Imported by both the React Hook Form on the client and the Zod `.parse()` call on the server — single source of truth for valid shapes.

### `src/generated/prisma/`

Generated by `prisma generate`. Never edit by hand; it's rewritten every time the schema changes. Imported as `@/generated/prisma/client`.

### `docs/`

These three files. Update them on **important** changes only:
- `TECH_STACK.md` — when adding/removing a library.
- `PROJECT_STRUCTURE.md` — when adding or repurposing a folder.
- `DESIGN_DECISIONS.md` — when a design decision is made or reversed.

## Request lifecycle — tracing one feature end-to-end

Creating an event by clicking a time slot:

1. User clicks a slot in `WeekView.tsx` → opens `EventDialog.tsx`.
2. User fills the form (managed by React Hook Form, validated by `schemas/event.ts`).
3. On submit, a TanStack Query mutation calls `POST /api/events` with JSON.
4. Next.js routes to `src/app/api/events/route.ts` (the `POST` export).
5. That handler imports `auth()` from `src/lib/auth.ts` to get the user session.
6. It re-validates the body with the *same* Zod schema from `src/schemas/event.ts`.
7. It calls `prisma.event.create(...)` via `src/lib/db.ts`.
8. Prisma talks to Postgres (running in the Docker container).
9. The handler returns the new row as JSON.
10. TanStack Query invalidates the events cache; `WeekView` re-fetches and the new block appears.
